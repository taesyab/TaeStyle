# Contribuir a TaeStyle

Antes de comenzar, revisar el diseño y la tarea del backlog. Mantener el alcance del MVP y registrar decisiones que cambien reglas o contratos.

## Cambios

- Ramas cortas desde main y un objetivo por pull request.
- Mensajes de commit claros; prefijos sugeridos docs, feat, fix, test y chore.
- Enlazar la tarea y explicar el comportamiento esperado.
- No incluir secretos, fotos reales ni datos personales.
- Actualizar documentación junto con cambios de comportamiento.

## Verificación

Para documentación: revisar enlaces relativos, consistencia con arquitectura y alcance. Para código futuro: compilar y ejecutar las pruebas relacionadas con el cambio; comprobar acceso por propietario, validaciones y estados de error cuando corresponda. Informar honestamente qué se probó y qué no se pudo probar.

No exigir pruebas de aplicación antes de que exista el proyecto ejecutable. Las verificaciones automáticas se incorporarán con la implementación.

## Terminado

Criterios de aceptación cumplidos, revisión realizada, comprobaciones pertinentes aprobadas y documentación actualizada. Una funcionalidad móvil requiere verificar su flujo completo, no solo su endpoint.
